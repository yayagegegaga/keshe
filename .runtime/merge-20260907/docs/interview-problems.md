# 面试问题应对：项目困难、解决方案和深挖回答

这份文档用于面试前准备。不要逐字硬背，建议按下面结构理解：

```text
问题现象 -> 排查过程 -> 解决方案 -> 为什么这样做 -> 可以怎么扩展
```

面试官喜欢听的不是“我用了某某技术”，而是你遇到了真实问题，并且能说清楚为什么这么解决。

## 一、总回答模板

如果面试官问：

> 你这个项目中遇到了哪些困难？你是怎么解决的？

可以先这样回答：

> 这个项目中我遇到的问题主要分为四类。第一类是业务状态流转比较复杂，比如救助工单、志愿任务、领养申请都不能随便修改状态；第二类是权限控制，普通用户只能操作自己的申请、通知、回访和文件，管理员可以看全局；第三类是事务一致性，比如领养成功时要同时修改申请状态、动物状态、关闭其他申请并写审核日志；第四类是联调环境问题，比如 MySQL、Redis、初始化 SQL 和登录异常。  
>  
> 我觉得最难的是领养成功这个流程，因为它不是单表更新，而是多个表之间要保持一致。我在 Service 层用状态机控制流程，并用事务保证多表操作要么全部成功，要么全部回滚。

# 二、项目中遇到的问题和解决方案

## 1. 登录接口一直返回“认证服务异常”

### 问题现象

登录 `admin / Admin@123`、`user / User@123` 时，接口没有返回 token，而是返回：

```text
认证服务异常，请检查数据库初始化或连接配置
```

前端无法进入首页，后续所有需要登录的接口都无法联调。

### 排查过程

我没有直接判断为账号密码错误，而是按顺序排查：

1. 先确认后端能否启动。
2. 访问 `/api/health` 和 `/doc.html`，确认 Spring Boot 和 Knife4j 正常。
3. 检查 `AuthServiceImpl`，发现 `InternalAuthenticationServiceException` 被统一包装，真实异常没有暴露。
4. 在认证异常处补充日志，打印真实堆栈。
5. 重新请求登录接口后，日志显示：

```text
java.sql.SQLException: Access denied for user 'root'@'localhost'
```

所以根因不是 JWT，也不是 BCrypt 密码不匹配，而是 MySQL 账号密码配置和本机实际环境不一致。

### 解决方案

我做了两点处理：

第一，`application-dev.yml` 支持环境变量覆盖：

```yaml
username: ${MYSQL_USERNAME:root}
password: ${MYSQL_PASSWORD:root}
```

这样不同电脑上不用改代码，可以通过环境变量传入自己的 MySQL 密码。

第二，认证异常处增加日志，方便以后快速定位真实原因。

### 面试回答

> 登录异常这个问题我印象比较深。一开始接口只返回认证服务异常，我不能确定是密码错、数据库错还是 Redis 错。后来我在认证异常处加了日志，发现真实原因是 MySQL 连接失败，`root/root` 和本机真实密码不一致。解决方式是让配置支持环境变量覆盖，并且保留详细日志，方便后续联调排查。

## 2. Redis 没启动导致登录失败

### 问题现象

系统登录逻辑是：

```text
账号密码认证成功 -> 生成 JWT -> 写入 Redis -> 返回 token
```

如果 Redis 未启动，登录 token 无法写入，登录流程无法完成。

### 排查过程

检测 Redis 端口：

```text
localhost:6379 连接失败
```

说明 Redis 没有启动。

### 解决方案

我没有吞掉 Redis 异常，因为登录 token 缓存是认证链路的一部分。  
如果登录接口返回成功但 token 没有缓存，后续请求校验会出现问题。

所以我让登录接口在 Redis 写入失败时返回明确提示：

```text
Redis 未启动或连接失败，请启动 Redis 后重试登录
```

同时在 README 中说明 Redis 的用途和启动要求。

### 面试回答

> Redis 在这个项目里主要用于登录 token 缓存和首页统计缓存。首页统计我做了降级，Redis 不可用时可以查数据库；但是登录 token 是认证闭环的一部分，所以 Redis 不可用时我选择明确报错，而不是假装登录成功。

## 3. 领养申请状态流转复杂，不能做普通 CRUD

### 问题现象

领养申请有多个状态：

```text
PENDING
FIRST_APPROVED
INTERVIEWING
TRIAL
SUCCESS
REJECTED
CANCELED
TRIAL_FAILED
```

如果只提供一个普通的修改状态接口，可能出现非法状态：

```text
PENDING -> SUCCESS
SUCCESS -> TRIAL
TRIAL -> REJECTED
CANCELED -> PENDING
```

这些都不符合业务规则。

### 解决方案

我在 Service 层维护允许的状态流转规则：

```text
PENDING -> FIRST_APPROVED / REJECTED / CANCELED
FIRST_APPROVED -> INTERVIEWING / REJECTED / CANCELED
INTERVIEWING -> TRIAL / REJECTED
TRIAL -> SUCCESS / TRIAL_FAILED
```

每次状态变更都调用统一校验方法：

```java
validateTransition(oldStatus, newStatus)
```

非法流转直接抛业务异常。

### 为什么放在 Service 层

状态流转是业务规则，不是请求转发逻辑。  
Controller 只负责接收参数，Service 才负责判断业务是否合法。

### 面试回答

> 我没有把领养申请做成简单 CRUD，而是按状态机处理。每个审核动作在修改状态前都要校验当前状态能不能流转到目标状态，这样可以防止非法流程。

## 4. 领养成功事务一致性最难

### 问题现象

领养成功不是只修改一张申请表，而是要同时完成：

1. 当前申请状态改为 `SUCCESS`
2. 动物状态改为 `ADOPTED`
3. 同一动物的其他未完成申请关闭
4. 写入 `adoption_review_log`
5. 生成站内通知

如果中间任何一步失败，都会造成数据不一致。

比如：

```text
申请已经 SUCCESS，但动物还是 TRIAL
动物已经 ADOPTED，但其他申请还在 PENDING
状态改了，但审核日志没写入
```

### 解决方案

在 `AdoptionServiceImpl.success()` 上使用事务：

```java
@Transactional(rollbackFor = Exception.class)
```

把下面操作放在同一个事务中：

```text
更新申请状态
更新动物状态
关闭其他未结束申请
写审核日志
生成通知
```

只要其中一步失败，整个事务回滚。

### 面试回答

> 我觉得最难的是领养成功事务。因为它涉及申请表、动物表、其他申请和审核日志，不是单表更新。我用 Spring 事务保证这些操作要么全部成功，要么全部回滚，避免出现部分成功导致的数据不一致。

## 5. 动物状态和领养申请状态容易混淆

### 问题现象

动物状态和领养申请状态是两个维度。

动物状态：

```text
ADOPTABLE
APPLYING
TRIAL
ADOPTED
```

申请状态：

```text
PENDING
FIRST_APPROVED
INTERVIEWING
TRIAL
SUCCESS
REJECTED
CANCELED
TRIAL_FAILED
```

两边都有 `TRIAL`，但含义不同。

### 解决方案

我拆成两个枚举：

```text
AnimalStatus
AdoptionApplicationStatus
```

然后在业务中明确同步关系：

```text
提交申请：ADOPTABLE -> APPLYING
进入试养：APPLYING -> TRIAL
领养成功：TRIAL -> ADOPTED
试养失败：TRIAL -> ADOPTABLE
```

### 面试回答

> 动物状态和申请状态不能混在一起。动物状态表示动物本身当前处于什么阶段，申请状态表示这条申请审核到哪一步。我用两个枚举分开管理，Service 中再做同步。

## 6. 重复申请同一动物的问题

### 问题现象

用户可能重复点击“申请领养”，导致同一用户对同一动物出现多条未结束申请。

### 解决方案

我定义了未结束状态：

```text
PENDING
FIRST_APPROVED
INTERVIEWING
TRIAL
```

提交申请时先查询：

```text
同一用户 + 同一动物 + 未结束状态
```

如果存在，则返回业务异常。

### 为什么不直接用唯一索引

因为用户被拒绝或取消后，未来是否允许再次申请可能会根据业务调整。  
用业务层判断更灵活。

### 面试回答

> 我没有简单地用唯一索引限制 user_id + animal_id，因为取消或拒绝后是否允许再次申请是业务策略问题。我在业务层判断未结束状态，既能防重复，也保留扩展空间。

## 7. 志愿者任务重复领取问题

### 问题现象

一个任务只能被一个志愿者领取。  
如果两个志愿者同时点击领取，普通的“先查再改”可能会出现并发问题。

### 解决方案

使用条件更新：

```sql
UPDATE volunteer_task
SET status = 'CLAIMED',
    volunteer_id = ?,
    start_time = NOW(),
    version = version + 1
WHERE id = ?
  AND status = 'WAIT_CLAIM';
```

如果影响行数是 1，说明领取成功。  
如果影响行数是 0，说明已经被别人领取或状态变化。

### 面试回答

> 任务领取我没有只做先查状态再更新，而是用 `UPDATE ... WHERE status = WAIT_CLAIM`，让数据库保证同一时间只有一个人能领取成功。

## 8. 工单状态流转和日志记录

### 问题现象

救助工单不能随便改状态。正确流程是：

```text
WAIT_ASSIGN -> ASSIGNED -> PROCESSING -> WAIT_CONFIRM -> CLOSED
```

如果没有校验，待分配工单可能直接被关闭，已关闭工单也可能被重新处理。

### 解决方案

Service 层做状态流转校验。  
每次状态变化都写入 `rescue_order_log`。

日志包括：

```text
工单 ID
操作人
原状态
新状态
操作类型
备注
操作时间
```

### 面试回答

> 工单模块我重点做了状态流转和日志。状态流转保证流程合法，日志用于追踪每一步是谁操作的，从什么状态变到什么状态。

## 9. 普通用户越权访问别人数据

### 问题现象

如果只判断用户是否登录，普通用户可能通过修改 ID 访问别人的数据：

```text
GET /api/adoptions/{id}
GET /api/follow-ups/{id}
PUT /api/notifications/{id}/read
DELETE /api/files/{id}
```

### 解决方案

两层控制：

第一层，管理员接口用：

```java
@PreAuthorize("hasAnyAuthority('ADMIN','SUPER_ADMIN')")
```

第二层，Service 层做数据归属校验：

```text
当前用户 ID == 数据所属用户 ID
```

比如：

- 通知只能标记自己的
- 回访只能查看自己的
- 文件只能删除自己上传的
- 管理员可以管理全局

### 面试回答

> 权限不能只靠前端隐藏按钮，也不能只判断是否登录。我的做法是管理员接口用注解限制，普通用户的数据归属在 Service 层校验，防止用户通过改 URL 或 ID 越权访问。

## 10. 文件上传安全问题

### 问题现象

文件上传有很多安全风险：

```text
空文件
超大文件
非法后缀
重名覆盖
路径穿越
服务器物理路径泄露
```

### 解决方案

我做了这些处理：

1. 禁止空文件
2. 限制最大 10MB
3. 只允许：

```text
jpg、jpeg、png、gif、webp、pdf
```

4. 用 UUID 生成存储名
5. 按日期目录保存
6. 清洗原始文件名
7. 路径归一化，防止路径穿越
8. VO 不返回 `file_path`，只返回 `file_url`

### 面试回答

> 文件上传我重点考虑了安全性。尤其是不把服务器物理路径返回给前端，只返回访问 URL；同时用 UUID 防止重名覆盖，并限制后缀和大小。

## 12. 首页统计缓存不能串用户数据

### 问题现象

首页统计一开始使用全局 key：

```text
statistics:overview
```

后来统计中加入了当前用户未读通知数。这个字段是用户维度的，如果还用全局 key，就可能 A 用户看到 B 用户的未读数。

### 解决方案

把缓存 key 改成：

```text
statistics:overview:{userId}
```

### 面试回答

> 加入未读通知数后，统计数据就不再完全是全局数据了。我把 Redis key 改成带 userId，避免不同用户之间缓存串数据。

## 16. Controller 容易堆业务逻辑

### 问题现象

如果 Controller 中写大量业务判断，项目会越来越乱。

### 解决方案

保持分层：

```text

```

### 面试回答

> 我尽量让 Controller 保持薄一点。比如状态流转、事务、防重复领取、权限归属都放在 Service 层，这样结构更清晰。

# 三、最难的问题怎么说

## 最难问题 1：领养成功事务

推荐回答：

> 我觉得最难的是领养成功流程。因为它不是单表更新，而是同时涉及申请表、动物表、其他申请和审核日志。如果中间某一步失败，就会出现数据不一致。  
>  
> 我的解决方案是在 Service 层用事务处理，先校验当前申请必须是 TRIAL，动物也必须处于 TRIAL，然后把申请改成 SUCCESS，把动物改成 ADOPTED，关闭其他未结束申请，并写入 adoption_review_log。这样整个流程要么全部成功，要么全部回滚。

## 最难问题 2：状态流转控制

推荐回答：

> 工单、任务和领养申请都有自己的状态流转。如果只是开放一个修改状态接口，很容易出现非法状态。我的做法是在 Service 层维护允许的状态变化，每次状态变化前统一校验，比如 PENDING 不能直接变 SUCCESS，已关闭工单不能再变处理中。

## 最难问题 3：权限越权控制

推荐回答：

> 权限控制难点在于不只是区分登录和未登录，还要判断这条数据是不是当前用户自己的。比如用户可以看自己的申请，但不能看别人的；可以标记自己的通知，但不能标记别人的。我的做法是管理员接口用注解控制，普通用户的数据归属在 Service 层校验。

# 四、面试官深挖模块时怎么回答

## 1. 深挖认证模块

### Q1：登录流程是怎样的？

回答：

> 用户提交用户名和密码后，后端通过 Spring Security 的 AuthenticationManager 认证。认证时会加载用户信息和角色，使用 BCrypt 校验密码。认证成功后生成 JWT，把 token 写入 Redis，并返回 token、用户信息和角色列表。后续请求通过 Authorization: Bearer token 携带 token。

### Q2：为什么要用 BCrypt？

回答：

> 明文存储密码不安全。BCrypt 会自动加盐，即使两个用户密码相同，生成的密文也不同，而且 BCrypt 计算成本较高，可以降低暴力破解风险。

### Q3：JWT 和 Redis token 同时用是不是重复？

回答：

> JWT 本身可以无状态认证，但纯 JWT 不方便主动退出登录。项目里把 token 存 Redis，是为了支持 logout 删除 token，也方便后续做 token 失效控制。所以 JWT 负责身份信息，Redis 负责服务端 token 状态。

### Q4：如果 Redis 挂了怎么办？

回答：

> 登录链路依赖 Redis 写 token，所以 Redis 不可用时登录会明确失败，提示启动 Redis。首页统计缓存不是强依赖，Redis 挂了会降级查数据库。

### Q5：为什么普通用户不能直接访问管理接口？

回答：

> 管理接口使用 `@PreAuthorize` 判断角色，比如 `ADMIN` 和 `SUPER_ADMIN` 才能访问。同时 Service 层还会校验数据归属，防止用户通过改 URL 越权访问。

## 2. 深挖权限模块

### Q1：你的 RBAC 是怎么设计的？

回答：

> 数据库里有 `sys_user`、`sys_role`、`sys_user_role` 三张表。用户和角色是多对多关系。登录时根据用户 ID 查询角色，转换成 Spring Security 的 GrantedAuthority，然后用 `@PreAuthorize` 控制接口权限。

### Q2：为什么权限判断不全写在前端？

回答：

> 前端隐藏按钮只能提升体验，不能保证安全。用户可以直接调接口或改 URL，所以真正的权限必须在后端校验。

### Q3：普通用户看自己的数据怎么实现？

回答：

> 这类权限不是单纯角色能解决的，需要数据归属校验。比如查看申请详情时，Service 会判断 `application.applicantId` 是否等于当前登录用户 ID；不相等且不是管理员，就返回 403。

### Q4：管理员和 SUPER_ADMIN 有什么区别？

回答：

> 当前项目中两者在业务管理权限上接近，`SUPER_ADMIN` 可以作为系统管理员预留给用户管理、角色权限配置等后续扩展。

## 3. 深挖救助工单模块

### Q1：工单状态有哪些？

回答：

```text
WAIT_ASSIGN 待分配
ASSIGNED 已分配
PROCESSING 处理中
WAIT_CONFIRM 待确认
CLOSED 已关闭
CANCELED 已取消
```

### Q2：状态流转怎么限制？

回答：

> 在 Service 层维护允许流转的状态集合，比如 `WAIT_ASSIGN` 只能变成 `ASSIGNED` 或 `CANCELED`，不能直接变 `CLOSED`。每个状态操作前都会调用统一校验方法。

### Q3：为什么要有工单日志？

回答：

> 工单是协同流程，管理员和志愿者都会操作。日志可以记录每一步是谁操作的，从什么状态变到什么状态，方便追溯，也更贴近真实管理系统。

### Q4：志愿者能不能处理别人的工单？

回答：

> 不能。Service 层会校验当前用户是不是工单的 handler。如果不是处理人，也不是管理员，就不允许开始或提交处理结果。

### Q5：管理员可以代志愿者处理吗？

回答：

> 当前设计里管理员拥有更高权限，可以进行管理类操作，比如分配、关闭。具体是否允许代处理要看业务，我在部分接口里允许管理员操作，是为了方便救助站管理场景。

## 4. 深挖志愿者任务模块

### Q1：任务和工单有什么区别？

回答：

> 工单通常来自救助线索，是救助流程的一部分；志愿者任务更偏日常协作，比如投喂、清理、送医、回访、临时救助，不一定来自用户线索。

### Q2：怎么防止任务重复领取？

回答：

> 使用条件更新，只有 `WAIT_CLAIM` 状态才能更新为 `CLAIMED`。如果同时有人领取，数据库只会让一个更新成功，另一个影响行数为 0，就返回任务已被领取。

### Q3：为什么不用 synchronized？

回答：

> synchronized 只能控制单个 JVM 内部线程，不适合数据库数据一致性。用数据库条件更新更可靠，即使以后部署多个实例也更容易扩展。

### Q4：任务完成记录怎么保存？

回答：

> 志愿者提交完成时，事务内同时更新任务状态为 `FINISHED`，并插入 `task_record`，保存完成内容和图片 URL。

## 5. 深挖领养申请模块

### Q1：为什么提交申请后动物要变 APPLYING？

回答：

> 当前项目采用“一只动物同一时间只处理一个领养流程”的简化策略。提交申请后动物从 `ADOPTABLE` 变成 `APPLYING`，避免多个用户同时申请导致审核流程复杂。

### Q2：如果要支持多人申请同一只动物怎么办？

回答：

> 可以不在提交申请时把动物改成 APPLYING，而是允许多个 PENDING 申请存在。管理员选择一个进入后续流程时，再把动物状态改成 APPLYING，并把其他申请保留排队或拒绝。这需要更复杂的申请优先级和并行审核策略。

### Q3：领养成功为什么要关闭其他申请？

回答：

> 因为动物已经被领养，同一只动物的其他未结束申请没有继续审核意义。关闭它们可以保证申请状态和动物状态一致。

### Q4：为什么 TRIAL 状态不能直接 REJECTED？

回答：

> 进入试养后，业务上不再是普通拒绝，而应该走试养失败 `TRIAL_FAILED`，这样能区分审核拒绝和试养失败两种业务原因。

### Q5：审核日志有什么用？

回答：

> 审核日志记录每次申请状态变化，包括审核人、原状态、新状态和备注。后续查看申请详情时，可以完整看到申请从提交到成功或失败的全过程。

### Q1：为什么只有 SUCCESS 申请才能新增回访？

> 回访是领养成功后的后续跟踪。如果申请还没成功，比如 PENDING 或 TRIAL，就不能算正式领养后的回访。

### Q2：普通用户能看哪些回访？

回答：

> 普通用户只能看 adopterId 等于自己的回访记录。管理员可以查看全部。

### Q3：回访删除为什么现在是物理删除？

回答：

> 当前版本为了简化实现采用物理删除。后续如果做审计，可以改成逻辑删除，并结合操作日志保留追溯信息。

### Q1：通知什么时候生成？

### Q2：为什么不用 WebSocket？

## 8. 深挖文件上传模块

### Q1：文件上传的完整流程是什么？

回答：

> 用户选择文件和业务类型，后端校验文件是否为空、大小是否超限、后缀是否合法。校验通过后用 UUID 生成存储名，按日期目录保存本地文件，然后写入 file_record，返回 fileUrl。

### Q2：为什么 VO 不返回 filePath？

回答：

> filePath 是服务器物理路径，暴露给前端有安全风险。前端只需要访问 URL，所以 VO 只返回 fileUrl、原文件名、业务类型、大小等安全字段。

### Q3：如何扩展 MinIO？

回答：

> 可以把 FileService 的本地保存逻辑抽象成存储策略。当前 file_record 已经保存了 fileUrl、fileType、uploaderId、bizId 等信息，后续把文件保存部分换成 MinIO 上传即可，业务层影响较小。

# 五、面试官常见追问

## Q：为什么不用微服务？

回答：

> 这个项目的复杂度主要在业务流程、权限和状态一致性，不在服务拆分。单体 Spring Boot 更适合当前规模，也更容易保证事务一致性。强行拆微服务会引入分布式事务和部署复杂度，反而不符合业务场景。

## Q：为什么不用消息队列？

回答：

> 当前通知只是站内通知，写数据库即可满足需求。没有异步削峰或复杂事件驱动需求，所以没有引入消息队列。

## Q：为什么不用定时任务？

回答：

> 当前没有必须定时执行的业务，比如自动回访提醒或过期申请处理。为了保持项目简洁，没有强行引入定时任务。

## Q：为什么不用 MinIO？

回答：

> 当前是本地演示和单体部署，本地存储足够。代码结构上保留了扩展空间，后续可以替换 FileService 的存储实现为 MinIO。

## Q：项目有哪些不足？

回答：

> 目前还有几个可优化点。第一，操作日志还没有做成 AOP 统一记录；第二，文件存储还是本地存储，后续可以扩展 MinIO；第三，前端路由和菜单可以做成动态权限菜单；第四，自动化测试还可以继续补充。  
> 但这些没有在当前版本强行加入，因为当前项目重点是把业务闭环、权限控制和状态流转讲清楚。

# 六、最推荐背熟的 5 段

## 1. 项目困难总述

> 这个项目最大的难点不是 CRUD，而是业务流程闭环。救助工单、志愿任务、领养申请都有状态流转，不能随便改状态；领养成功涉及多张表，需要事务保证一致性；普通用户和管理员权限不同，还要防止越权访问别人的数据。

## 2. 最难问题

> 我觉得最难的是领养成功事务。因为它不仅要把申请改成 SUCCESS，还要把动物改成 ADOPTED，并关闭其他未结束申请，还要写审核日志。如果中间某一步失败，就会出现数据不一致。所以我把它放在 Service 层事务里处理。

## 3. 真实排查问题

> 最后联调时我遇到过登录接口一直返回认证服务异常。一开始我以为是密码或 JWT 问题，后来在认证异常处加日志，发现真实原因是 MySQL 配置的 root/root 和本机实际密码不一致，日志里是 Access denied。后来我把配置改成支持环境变量覆盖，并且 Redis 未启动时也返回更明确的错误提示。

## 4. 权限控制

> 权限控制我分两层做。管理员接口用 `@PreAuthorize` 限制角色，普通用户自己的数据在 Service 层校验归属，比如申请、通知、回访、文件都要判断是否属于当前用户。这样即使前端被绕过，后端也能拦住。

## 5. Redis 使用

> Redis 主要用于登录 token 缓存和首页统计缓存。首页统计只是优化，所以 Redis 不可用时可以降级查数据库；登录 token 是认证链路的一部分，所以 Redis 不可用时会明确提示启动 Redis。

1. 登录接口一直返回“认证服务异常”
问题现象
一开始登录 admin / Admin@123、user / User@123 时，接口没有返回 token，而是返回：
认证服务异常，请检查数据库初始化或连接配置
前端也无法进入首页，导致后面所有需要登录的接口都没法联调。
排查过程
我没有直接认为是账号密码错，而是按顺序排查：
先看 application-dev.yml，确认当前连接的是 stray_animal 数据库，用户名密码默认是 root/root。
再确认后端是否真的启动成功，/api/health 和 /doc.html 都能访问，说明 Spring Boot 本身没问题。
然后看登录代码，发现 AuthServiceImpl 对 InternalAuthenticationServiceException 做了统一包装，真实异常被隐藏了。
我在认证异常处补了日志，把真实异常打印出来。
再次登录后，日志显示：
java.sql.SQLException: Access denied for user 'root'@'localhost'
所以真实原因不是 BCrypt 密码错，也不是 JWT 问题，而是 MySQL 账号密码配置和本机实际环境不一致。
解决方案
我做了两件事：
第一，修改 application-dev.yml，支持环境变量覆盖：
username: ${MYSQL_USERNAME:root}
password: ${MYSQL_PASSWORD:root}
这样不同电脑上不用改代码，可以用环境变量指定自己的 MySQL 密码。
第二，优化登录异常日志。之前只返回“认证服务异常”，现在后端日志会记录真实原因，方便排查。
面试回答总结
这个问题让我意识到，不能只看前端返回的信息，要看后端日志和异常堆栈。我最后定位到是 MySQL 连接认证失败，不是登录逻辑本身的问题。解决方式是让配置支持环境变量，并在认证异常处打印真实日志，后续排查会更方便。

2. Redis 没启动导致登录失败
问题现象
登录逻辑是：账号密码认证成功后生成 JWT，然后把 token 写入 Redis。
如果 Redis 没启动，登录后写 token 会失败。
排查过程
我用端口检测发现：
localhost:6379 连接失败
说明 Redis 没有启动。而且本机没有 redis-cli，所以也无法直接查 Redis key。
解决方案
我没有把 Redis 异常吞掉，因为登录 token 缓存是认证闭环的一部分。如果 Redis 不可用，用户登录成功但 token 没缓存，后续请求也会出问题。
所以我在登录写 Redis 时捕获异常，返回更明确的提示：
Redis 未启动或连接失败，请启动 Redis 后重试登录
同时在 README 写清楚 Redis 的用途和启动要求。
面试回答总结
Redis 在这个项目里主要用于登录 token 缓存和首页统计缓存。统计缓存我做了降级，Redis 不可用时可以查数据库；但是登录 token 缓存是认证链路的一部分，所以 Redis 没启动时我选择明确报错，而不是假装登录成功。

3. 领养申请不是普通 CRUD，状态流转容易乱
问题现象
领养申请有很多状态：
PENDING
FIRST_APPROVED
INTERVIEWING
TRIAL
SUCCESS
REJECTED
CANCELED
TRIAL_FAILED
如果只是写一个普通的 update status 接口，很容易出现非法状态，比如：
PENDING -> SUCCESS
SUCCESS -> TRIAL
TRIAL -> REJECTED
CANCELED -> PENDING
这些在业务上都是不允许的。
解决方案
我在 Service 层设计了状态流转表，只允许指定状态变化。
例如：
PENDING -> FIRST_APPROVED / REJECTED / CANCELED
FIRST_APPROVED -> INTERVIEWING / REJECTED / CANCELED
INTERVIEWING -> TRIAL / REJECTED
TRIAL -> SUCCESS / TRIAL_FAILED
每次状态变化前都调用统一方法校验：
validateTransition(oldStatus, newStatus)
如果不在允许范围内，就抛业务异常。
为什么放在 Service 层
因为状态流转是业务规则，不应该写在 Controller。Controller 只负责接收请求，Service 才负责判断“这个状态能不能变”。
面试回答总结
我没有把领养申请做成简单 CRUD，而是按业务状态机处理。每个审核动作不是直接改字段，而是先校验当前状态能不能流转到目标状态。这样可以防止非法状态，也方便面试讲解业务逻辑。

4. 领养成功时多表事务一致性最难
问题现象
领养成功不是只改一张申请表。它至少要做这些事：
当前申请状态改为 SUCCESS
动物状态改为 ADOPTED
同一动物的其他未结束申请要关闭
写入领养审核日志
后续还要生成通知
如果中间任何一步失败，就会出现数据不一致。
比如：
申请已经 SUCCESS
但动物状态还是 TRIAL
或者其他申请还在 PENDING
这会导致业务数据混乱。
解决方案
我在 AdoptionServiceImpl.success() 上加了事务：
@Transactional(rollbackFor = Exception.class)
把这些操作放在同一个事务里：
修改当前申请状态
修改动物状态
关闭其他未结束申请
写 adoption_review_log
生成 notification
只要其中一步失败，整个事务回滚。
为什么这是最难的
因为它涉及多个业务概念：
领养申请状态
动物状态
其他申请状态
审核日志
通知
这些表之间必须保持一致。
面试回答总结
我觉得项目里最难的是领养成功事务。它不是单表更新，而是多个表之间要保持一致。我用 Spring 事务把申请状态、动物状态、其他申请关闭和审核日志写入放在一个事务中，避免出现部分成功、部分失败的数据问题。

5. 动物状态和领养申请状态容易混淆
问题现象
一开始设计时，很容易把动物状态和申请状态混在一起。
动物状态是：
ADOPTABLE
APPLYING
TRIAL
ADOPTED
申请状态是：
PENDING
FIRST_APPROVED
INTERVIEWING
TRIAL
SUCCESS
REJECTED
CANCELED
TRIAL_FAILED
两者都有 TRIAL，但含义不同：
动物的 TRIAL：这只动物正在试养中
申请的 TRIAL：这条申请进入试养阶段
解决方案
我把它们拆成不同枚举：
AnimalStatus
AdoptionApplicationStatus
在业务代码里明确区分：
用户提交申请：动物 ADOPTABLE -> APPLYING
进入试养：动物 APPLYING -> TRIAL
领养成功：动物 TRIAL -> ADOPTED
面试回答总结
这个项目里动物状态和申请状态是两个不同维度。我专门拆成两个枚举，避免用一个 status 字段表达所有含义。这样代码更清晰，也能避免业务判断混乱。

6. 同一用户重复申请同一动物的问题
问题现象
如果用户重复点击“申请领养”，可能会产生多条未结束申请。这样管理员审核时就会混乱。
解决方案
我定义了“未结束状态”：
PENDING
FIRST_APPROVED
INTERVIEWING
TRIAL
提交申请时，先查询当前用户对该动物是否已经存在这些状态的申请。
如果存在，就返回业务异常：
不能重复申请同一只动物
为什么没有直接用唯一索引
因为如果用户之前的申请已经 REJECTED 或 CANCELED，未来是否允许再次申请可能是业务策略问题。
所以我先用业务层判断“未结束申请不能重复”，更灵活。
面试回答总结
我没有简单地给 user_id + animal_id 加唯一索引，因为取消或拒绝后是否允许再次申请可能变化。我在业务层判断未结束状态，既能防重复，又保留了后续扩展空间。

7. 志愿者任务重复领取问题
问题现象
一个任务只能被一个志愿者领取。如果两个志愿者几乎同时点击领取，普通的先查后改可能会出现并发问题。
解决方案
我使用条件更新：
UPDATE volunteer_task
SET status = 'CLAIMED',
    volunteer_id = ?,
    start_time = NOW(),
    version = version + 1
WHERE id = ?
  AND status = 'WAIT_CLAIM'
如果影响行数是 1，说明领取成功。
如果影响行数是 0，说明任务已经被别人领取或状态变化，返回业务异常。
为什么这样做
比单纯先查询再更新更可靠，因为状态判断和更新在数据库层一次完成。
面试回答总结
任务领取我没有只做“先查状态再更新”，而是用 update where status = WAIT_CLAIM 的方式，让数据库帮我保证同一时间只有一个人能领取成功。

8. 工单状态流转和日志记录
问题现象
救助工单有完整流程：
WAIT_ASSIGN -> ASSIGNED -> PROCESSING -> WAIT_CONFIRM -> CLOSED
如果没有后端控制，用户可能直接把待分配工单改成已关闭，或者已关闭工单又改回处理中。
解决方案
我给工单也做了状态流转校验，并且每次状态变化都写入 rescue_order_log。
日志内容包括：
工单 ID
操作人
原状态
新状态
操作类型
备注
操作时间
面试回答总结
工单模块我重点做了状态流转和日志。状态流转保证业务流程合法，日志用于追踪每一步是谁操作的、从什么状态变到什么状态，这比单纯 CRUD 更贴近真实系统。

9. 普通用户越权查看别人数据的问题
问题现象
很多接口如果只写“登录即可访问”，会有越权风险。比如：
GET /api/adoptions/{id}
GET /api/follow-ups/{id}
PUT /api/notifications/{id}/read
DELETE /api/files/{id}
普通用户如果猜到别人的 ID，就可能访问别人的数据。
解决方案
我做了两层控制：
第一层：Controller 上用 @PreAuthorize 控制管理员接口。
第二层：Service 内部做数据归属校验。
比如文件删除：
管理员可以删除全局文件
普通用户只能删除自己上传的文件
通知已读：
只能标记自己的通知
回访详情：
管理员可以看全部
普通用户只能看 adopter_id 是自己的记录
面试回答总结
权限不能只靠前端隐藏按钮，也不能只靠接口是否登录。我在 Service 层根据当前用户 ID 和数据归属做校验，防止用户通过改 URL 或 ID 访问别人的数据。

10. 文件上传安全问题
问题现象
文件上传如果不控制，会有很多风险：
上传空文件
上传超大文件
上传非法后缀
文件重名覆盖
原始文件名带路径穿越
前端拿到服务器物理路径
解决方案
我做了这些控制：
禁止空文件
限制大小，默认 10MB
只允许：
jpg、jpeg、png、gif、webp、pdf
使用 UUID 生成存储文件名
按日期目录保存
清洗原始文件名
使用路径归一化，防止路径穿越
前端 VO 不返回 file_path，只返回 file_url
面试回答总结
文件上传我重点考虑了安全性。尤其是不把服务器物理路径暴露给前端，只返回访问 URL。同时用 UUID 防止重名覆盖，用后缀和大小限制控制上传风险。

11. 文件记录绑定业务 ID 的问题
问题现象
第七阶段时，文件记录只有业务类型，比如：
ANIMAL_IMAGE
TASK_IMAGE
FOLLOW_UP_IMAGE
但不知道具体属于哪条动物、任务或回访记录。
解决方案
我在 file_record 表新增了 biz_id 字段。
这样：
ANIMAL_IMAGE 可以绑定 animal_id
TASK_IMAGE 可以绑定 volunteer_task_id
FOLLOW_UP_IMAGE 可以绑定 follow_up_record_id
RESCUE_ORDER_IMAGE 可以绑定 rescue_order_id
并且文件查询支持按 bizType、bizId、上传人、文件名关键词筛选。
面试回答总结
这个优化让文件不只是孤立记录，而是能和具体业务数据关联起来。后续如果做动物图片列表、任务完成照片、回访照片展示，就可以直接按业务 ID 查询。

12. 首页统计缓存不能把不同用户的数据串掉
问题现象
首页统计一开始使用全局 Redis key：
statistics:overview
后来统计里加入了“当前用户未读通知数”。这个字段是用户维度的，如果还用全局 key，就可能出现 A 用户看到 B 用户未读通知数的问题。
解决方案
把缓存 key 改成用户维度：
statistics:overview:{userId}
这样每个用户有自己的首页统计缓存。
面试回答总结
统计缓存加入用户相关字段后，不能再用全局缓存。我把 key 改成带 userId 的形式，避免不同用户之间的数据串缓存。

13. Redis 缓存统计，但不能影响接口可用性
问题现象
首页统计只是优化性能，不应该因为 Redis 挂了就导致首页完全不可用。
解决方案
统计接口读取 Redis 时加了降级：
先尝试读取 Redis
读不到或 Redis 异常，就查数据库
查完再尝试写 Redis
写 Redis 失败也不影响接口返回
面试回答总结
Redis 在统计这里是优化手段，不是强依赖。所以我做了降级处理，Redis 不可用时仍然查数据库返回，保证功能可用。

14. SQL 初始化数据重复执行报错问题
问题现象
项目反复初始化数据库时，如果 data.sql 直接 insert，可能因为主键或唯一索引重复报错。
解决方案
初始化数据采用：
ON DUPLICATE KEY UPDATE
这样重复执行时不会直接失败，而是更新已有数据。
面试回答总结
为了方便本地反复演示和初始化，我让 data.sql 尽量可重复执行，避免因为重复主键导致导入失败。

16. Controller 不能堆业务逻辑
问题现象
项目模块越来越多后，如果 Controller 里写太多业务判断，代码会很乱，也不方便测试和维护。
解决方案
我保持分层：
Controller：接收参数、调用 Service、返回 Result
Service：业务规则、权限归属、状态流转、事务
Mapper：数据库操作
DTO：接收请求
VO：返回前端
Enum：状态和类型统一管理
面试回答总结
我比较注意分层。比如领养成功事务、状态流转、防重复领取都放在 Service 层，Controller 不写复杂业务，这样结构更清晰。

17. 前端构建时 Vite 临时文件权限问题

vite.config.js.timestamp-xxx.mjs
有时会因为权限问题失败。
解决方案
确认这不是代码错误，而是环境权限问题。用有权限的构建环境重新执行后，构建通过。
面试回答总结
我区分了代码错误和环境错误。这个问题不是 Vue 代码编译失败，而是 Vite 在当前环境写临时文件被拒绝。有权限环境下重新构建可以通过。

18. 前端角色菜单控制问题
问题现象
不同角色看到的功能入口不一样：
普通用户不应该看到管理入口
志愿者需要看到任务和工单
管理员需要看到审核和管理入口
解决方案
前端通过 Pinia 保存 userInfo.roles，首页根据角色显示不同按钮。
但我没有只依赖前端控制，后端仍然用 @PreAuthorize 和 Service 归属校验做最终保护。
面试回答总结

最难的几个问题怎么回答
如果面试官问：“你觉得最难的问题是什么？”
你可以从这 3 个里选。
最难问题 1：领养成功事务一致性
可以这样说：
我觉得最难的是领养成功这个流程。因为它不是单表更新，而是要同时修改领养申请、动物状态、其他未完成申请，还要写审核日志。如果中间某一步失败，就会出现动物状态和申请状态不一致的问题。
我的解决方式是在 Service 层使用事务，把这些操作放在同一个事务方法里，并且在执行前校验当前申请必须是 TRIAL，动物也必须是 TRIAL。成功后申请变成 SUCCESS，动物变成 ADOPTED，其他未结束申请自动关闭，并写入 adoption_review_log。这样保证整个领养成功流程要么全部成功，要么全部回滚。

最难问题 2：状态流转设计
可以这样说：
项目中工单、任务、领养申请都有状态流转。如果只是开放一个修改状态接口，很容易出现非法状态。我的做法是把允许的状态变化定义在 Service 层，比如 Map 结构或者统一校验方法，每次状态变化前都调用 validateTransition。这样 Controller 不关心业务规则，Service 统一保证状态合法。

最难问题 3：权限越权问题
可以这样说：
权限控制也比较难，因为不是简单地区分登录和未登录，还要区分“是不是自己的数据”。比如普通用户可以看自己的领养申请，但不能看别人的；可以标记自己的通知已读，但不能标记别人的；可以删除自己上传的文件，但不能删除别人的文件。
我的做法是管理员接口用 @PreAuthorize 控制，数据归属在 Service 层再校验当前用户 ID。这样即使前端被绕过，后端也能拦住越权操作。

面试官追问素材
Q：为什么不用微服务？
可以答：
这个系统面向校园和救助站场景，业务复杂度主要在流程和权限，不在高并发或服务拆分。用单体 Spring Boot 更容易保证事务一致性，也更适合当前项目规模。强行拆微服务反而会增加分布式事务、部署和维护成本。

Q：为什么 Redis 只用来缓存统计和 token？
可以答：
因为这个业务没有秒杀或高并发场景，不需要硬包装 Redis。Redis 在这里主要有两个合理用途：登录 token 缓存和首页统计缓存。首页统计涉及多表 count，缓存 5 分钟可以减少重复查询。

Q：为什么文件上传不用 MinIO？
可以答：
当前项目是单体演示系统，本地存储足够满足需求。我在代码结构上保留了扩展空间，比如文件记录表保存 URL、路径、业务类型和上传人，后续替换为 MinIO 时主要改 FileService 的存储实现即可。

Q：你怎么保证接口返回统一？
可以答：
项目里统一使用 Result<T> 返回，分页统一用 PageResult<T>。异常通过 GlobalExceptionHandler 统一处理，业务异常抛 BusinessException，这样前端可以统一处理 code、message、data。

Q：为什么要用 DTO 和 VO？
可以答：
DTO 用来接收前端请求，VO 用来返回前端展示。这样可以避免直接暴露 Entity，比如文件记录 Entity 里有服务器物理路径 filePath，但 VO 不返回这个字段，避免敏感信息泄露。

可以主动说的项目不足
面试官如果问“不足和优化方向”，不要说“没有不足”。可以答：
这个项目目前还有一些可以优化的地方。比如操作日志还没有做成 AOP 统一记录；文件存储目前是本地存储，后续可以扩展 MinIO；前端菜单权限现在是基于角色简单控制，后续可以做成动态菜单；另外还可以补充更多自动化测试和接口测试集合。
但我没有在当前版本强行引入这些，因为项目定位是单体业务系统，当前重点是把救助、领养、回访、通知的业务闭环跑通。

最推荐你背熟的 3 段
第一段：项目难点总结
这个项目最大的难点不是 CRUD，而是业务流程闭环。比如救助工单、志愿任务、领养申请都有状态流转，状态不能随便改；领养成功还涉及申请表、动物表、其他申请和审核日志，所以要用事务保证一致性；另外普通用户和管理员权限不同，还要防止用户越权访问别人的数据。

第二段：最难问题
我觉得最难的是领养成功事务。因为领养成功时不仅要把申请改成 SUCCESS，还要把动物改成 ADOPTED，并关闭其他未结束申请，还要写审核日志。如果其中一步失败，就会出现数据不一致。所以我把它放在 Service 层事务里处理，并且在执行前校验申请状态和动物状态。

第三段：真实排查问题
项目最后联调时我遇到过登录接口一直返回认证服务异常。一开始以为是密码或者 JWT 问题，后来我在认证异常处加日志，发现真实原因是 MySQL 配置的 root/root 和本机实际密码不一致，日志里是 Access denied。后来我把配置改成支持环境变量覆盖，并且 Redis 未启动时也返回更明确的错误提示。这个问题让我意识到联调时要先看真实异常堆栈，不能只看前端提示。
